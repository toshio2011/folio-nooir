# Folio Nooir browser emulator — release gate update (2026-11-04)

This report supersedes the earlier preliminary assessment in
[`web-emulator-readiness.md`](web-emulator-readiness.md). The emulator is **not
ready for public Pages deployment yet**: the pinned engine needs a fresh Linux
WASM build, the new licensed-ROM boot smoke, and inspection of the exact
generated package. The build-only workflow is prepared for that validation.

The work is isolated on `codex/nooir-web-emulator-beta` at Folio Nooir v1.6.6
commit `b6d428a3187afc25d434fcb475e9ab436099c1ba`. X4 Pro and X4 Classic are
disabled. No v1.6.7 source, official firmware asset, device, or release was
modified. No firmware is included in the source branch or intended site
package.

The package allows only four hash-locked emulator `.bin` files: the C3 ROM,
C3 bootloader, CrossPoint NVS seed, and partition image. It rejects unknown
`.bin`, `.xota`, `.elf`, `.pem`, private-key and credential-file entries. It
also checks the exact pinned ROM-notice Git objects, package root contents,
corresponding-source members, and common credential patterns in text files.

The local synthetic package audit is **not a passing final-package result**:
its fixture reused a prebuilt web-dist but did not contain the resolved QEMU
Meson subproject checkout. The audit correctly rejected the missing
subproject license texts. Those sources are populated by the actual Linux
build; the workflow must prove that the freshly produced package includes them
before publication.

## Build and test evidence

- Local ROM preparation succeeded: `esp32c3-rom.bin`, 387,784 bytes,
  SHA-256 `3336ae473a063be8dae6790bd45fee4506f2cf273aa36f3dfd9e0495ecb665cc`.
- The existing packaged wrapper previously booted the unchanged official
  v1.6.6 firmware under X3 and X4, verified virtual input, EPUB reading, SD
  persistence, and X4 reading-position persistence. That older run used the
  then-current upstream ROM support image. It does **not** validate boot with
  the newly substituted Espressif ROM; the workflow now performs this separate
  X3/X4 smoke before packaging.
- Pinned Node tests: 115 passed on Windows. Two host-tool-dependent test files
  were omitted locally; the Ubuntu workflow installs `dosfstools` and `mtools`
  and runs the complete suite.
- The web-emulator Python contract suite passed 8/8 after the license changes.
  The existing Nooir regression record from this v1.6.6 workstream reports
  148 Python tests and native CTest 585/585 passed.
- The GitHub Pages workflow has not yet run. It is configured to build and
  upload a seven-day review artifact; deployment remains hard-disabled.

## Functional scope and current limitations

Original X4 is the initial profile; X3 uses the same official 1.6.6 firmware
and its dedicated machine profile. Earlier browser validation covered
480×800 X4 and 528×792 X3 display output, Home/library navigation, virtual
buttons, EPUB page turns, serial readiness output, and browser-local FAT32 SD
and progress persistence. Automatic stable firmware byte-loading remains
unsupported by the cross-origin release redirect. This is accepted for beta:
the page discovers the stable release, links to GitHub, and asks users to
select the downloaded local `.bin`.

The new licensed-ROM smoke, full fresh engine build, final source/license
package audit, browser smoke against the generated artifact, and GitHub Pages
artifact review remain required. Physical device testing is pending; emulator
results do not establish physical firmware safety. No device flashing is part
of this work.

## Current X3 failure follow-up (2026-11-04)

The authorized sign-in completed and the isolated branch is now pushed at
`59abd219b4e13ee0c2f1da8a06f0563580b69bfe`; draft PR #3 remains open. The
latest build-only run is `41783095009`. Tests, dependency build, full WASM
build, official ROM download/checksum, and exact v1.6.6 firmware checksum
passed. X3 smoke failed before expected SPI boot output; packaging, audit,
and review-artifact upload did not run. The failure log artifact is
`13301086190` (1,295 bytes; SHA-256
`844e8a9e20efde1becaa9e466ffc07b134f5bc58f9095ffdd634b2b70570450a`; expires
2026-11-07).

Its C3 panic reports `PC=0x4004cc4e`, `MCAUSE=5`, and `MTVAL=0x1b`. The
checksum-verified Espressif ROM ELF maps this to `spi_dummy_len_fix`; the
faulting instruction reads offset `0x1b` through a null base, and ELF symbol
`0x3fcdfff0` is `rom_spiflash_legacy_data`. Both the 20260528 and 20230320
official release archives were checksum-verified, and contain the same
`esp32c3_rev3_rom.elf` SHA-256
`19ac22e08707df926fb0cf4c54795d4067b983fae8635f396ded173a6d78fc3c`.
Its load-image data at offsets `0x59590`/`0x59664` is zero. The pinned
emulator ROM has nonzero bytes in this initialization region; the reviewed
Espressif ELF conversion differs there in 1,022 bytes. This is the leading
explanation for the panic, but still needs a licensed, boot-validated fix.

The pinned ROM's exact SHA-256 is also the SHA-256 of Espressif QEMU's
`pc-bios/esp32c3-rom.bin`. Espressif's introducing commit says that it
includes the C3 BIOS, but no file-level license or redistribution notice was
found for that binary. This leaves that alternative unresolved and excluded
from the web distribution. Do not copy its missing initialization values into
the Apache ELF or use that blob until its terms are clarified. Current ELF
license terms remain clear, but its image is not functionally compatible with
the pinned engine's boot path as configured.

Accordingly, the workflow still has no passing X3/X4 licensed-ROM smoke and
no package artifact to inspect. Do not deploy Pages. No physical device was
flashed. X4 Pro/Classic remain disabled; physical X3/X4 testing remains
pending. The main firmware CI also remains blocked at the unchanged
unavailable FreeInk SDK submodule commit.
